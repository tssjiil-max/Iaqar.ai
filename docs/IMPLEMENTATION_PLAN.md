## Principal risks

- Firestore rules cannot independently calculate every Unicode normalization
  transformation. Claim IDs are generated by trusted shared normalization code,
  while rules enforce ownership and transaction consistency.
- Existing office records may not yet have separate logo/display/cover URLs or
  category preferences; client defaults must remain backward-compatible.
- R2 and FCM production connectivity cannot be proven from repository tests
  without deployed credentials and real provider tests.
- `publicOffices` currently permits anonymous collection reads. Tightening this
  without a server lookup endpoint would break the existing public slug query;
  the current public projection therefore must remain minimal until that
  endpoint is added in a separately scoped security change.
- The current Worker is monolithic. Changes must remain narrow to avoid
  destabilizing connected intake and matching paths.
