## الهدف الثابت
تطوير الموقع القائم لا إنشاء موقع جديد. عقل مركزي واحد (نظام تشغيل موثوق + تنسيق)، قاعدة بيانات مركزية مع عزل صارم بين المكاتب، ومحركات أعمال قابلة للعمل بدون AI. ثلاثة أدوار اختيارية: وكيل المطابقة، وكيل المعاينة، وكيل التفاوض. إضافة وكيل رابع مستقبلاً عبر عقد واجهة ثابت دون تعديل محركات الأعمال.

## حقائق ينبغي التحقق منها في الكود
- Firestore بمسارات offices/{officeId}، Cloudflare Worker، واجهات Firebase، workflow/matching.
- المستخدم أفاد أن المطابقة تعمل عبر الموقع، وأن طلبات واتساب لا تظهر في لوحة المكتب. هذا وصف سلوكي من المستخدم، وليس تشخيصًا مؤكداً للسبب.
- README-AR.txt يذكر أن الإرسال التلقائي الخارجي عبر واتساب معطل، وأن المطابقة داخل المكتب نفسه. تحقق من التنفيذ والاختبارات والإعدادات؛ لا تفترض صحة النشر من الوثائق وحدها.
- قد توجد إعدادات Meta وWebhook؛ لا تعرض أسرارًا أو تعدّلها.

## تعليمات التنفيذ الحاكمة
1. لا تلمس main ولا تنشر أي تحديث ولا تربط خدمات مدفوعة ولا تحذف بيانات حية. التغييرات فقط في الفرع المذكور وعلى بيانات اصطناعية ومحاكيات.
2. قبل تعديل أي منطق: اقرأ شجرة الملفات، الدوال المهمة والاختبارات، ثم قدم ملفًا يتضمن خريطة الاعتماديات، المسارات، الجداول، ومخاطر العزل والتكامل.
3. أضف اختبارات فاشلة أولًا للسلوك المطلوب، ثم أصلح أقل قدر ممكن من الكود، ثم شغّل الاختبارات والتدقيق.
4. لا تبدّل محرك المطابقة الناجح على الويب ولا تنشئ محركًا آخر لواتساب؛ كل القنوات تستخدم عقد إدخال موحدًا مع officeId موثّق من الخادم، source، sourceMessageId، consent/status، ومنع تكرار.
5. لا تعرّف officeId القادم من العميل بوصفه إثبات صلاحية. تحقق من Firebase Auth والعضوية أو الربط الرسمي لهوية رقم Meta.
6. مصادقة الوكلاء وتفويض الأدوات وتقييد نطاق البيانات والتحقق من المخرجات تتم في الخادم؛ لا تجعل تعليمات النموذج أو UI مصدرًا للصلاحية.
7. اجعل أوضاع التشغيل للمكتب manual/rules/AI، والوظائف الأساسية لا تتوقف عند تعطيل AI.
8. أي تفاوض ملزم أو تعديل عمولة أو عقد أو مشاركة معلومات شخصية يحتاج موافقة الطرف المخوّل والتحقق النظامي؛ لا رسائل آلية خارجية بدون موافقات وضبط Meta.
9. اختبر مكتبًا واحدًا ثم خمسة مكاتب بعزل صارم، دون إرسال بيانات شخصية بين المكاتب إلا بتصريح.

## مراحل التنفيذ ومعايير القبول
### المرحلة 0: تقرير تدقيق — بلا تعديل سلوكي
- قارن الوضع الفعلي بالرؤية، وصنف احتفاظ/إصلاح/إعادة تنظيم/تعطيل مؤقت/حذف مشروط.
- وثّق مسار meta/webhook إلى inbox ثم clients/owners ثم matches ثم alerts؛ افصل الحقائق المثبتة عن الاحتمالات.
- احصر حقول المصادر والأحياء والسعر ونوع الصفقة والخصوصية.
- راجع Firestore rules وworker endpoints وسيناريوهات سوء استخدام officeId.

### المرحلة 1: إصلاح استقبال واتساب
- اختبارات: حدث Meta صحيح -> تحديد office من Phone Number ID -> رسالة خاصة -> parsing -> حفظ في نفس المكتب -> استدعاء محرك المطابقة القائم -> تسجيل نتيجة أو سبب عدم وجود مطابقة.
- اختبارات سلبية: توقيع Webhook غير صحيح، رقم غير مربوط، تكرار message ID، رسالة حالة وليست نصاً، رسائل خالية، تداخل مكتبين، عدم توافر API خارجي.
- لا تغيّر إعدادات الإنتاج؛ إن كان حفظ السجل يتطلب موافقة بشرية، احفظه pending ولا تطابقه كمعتمد حتى الموافقة.
- لا تعتبر اختبارات المحاكي دليلاً على نجاح Meta الحقيقي.

### المرحلة 2: تنظيم العقل المركزي تدريجيًا
- حدود وحدات منطقية (بدون تفكيك مكلف إلى microservices): ingestion, registry/tenancy, matching, scheduling/viewing, negotiation, workflow, compliance, integrations, agent-orchestrator.
- خطط لترحيل آمن من worker/src/index.js بخطوات صغيرة واختبارات توافق للواجهات الحالية.
- تعريف واضح للأحداث (record.received, record.approved, match.found, viewing.requested, negotiation.updated, deal.closed) مع idempotency.
- Feature flags لكل مكتب وعزل مصادر البيانات، وسجل تدقيق وتتبع للأحداث.

### المرحلة 3: ثلاثة وكلاء قابلون للتعطيل
- Match Agent: يستدعي matching service الحالي، يرتب ويشرح النتائج؛ لا يغيّر أسعارًا ولا يكشف بيانات طرف ثالث.
- Viewing Agent: يقترح مواعيد معاينة ويسجل قبولها، ويستخدم Calendar كتكامل اختياري عند الإذن.
- Negotiation Agent: يدير عروضًا منظمة بالأزرار والحالات وقبول/رفض/عرض مقابل، ويصعّد الحالات الحساسة للوسيط؛ لا ينشئ عقودًا ملزمة تلقائيًا.
- Agent interface: {agentId, version, capabilities, allowedTools, officeScope, requiresApproval, enabled}; تسجيل الأدوات ونتائجها، timeout، retries، circuit breaker، fallback يدوي.
- أثبت باختبار إضافة Agent رابع تجريبي dummy دون تعديل المنطق الأساسي وبإمكان إيقافه دون تعطيل الآخرين.

### المرحلة 4: تجربة خمسة مكاتب
- مستخدمو مكتب A لا يرون السجلات الخاصة بمكتب B، إلا فرص تعاون مصرح بها مع أقل قدر لازم من البيانات.
- الرابط الخاص يعين المكتب، والرابط العام يجري مطابقة أولية ويوزع حسب الأحياء وفق قواعد موثقة.
- عمولة التعاون الافتراضية 50/50 فقط عند موافقة الطرفين؛ أي نسبة مختلفة باتفاق واضح.
- لا نشر إعلانات للعامة؛ استلام طلبات وعروض خاصة لا يعفي من المتطلبات النظامية للوساطة والخصوصية.
