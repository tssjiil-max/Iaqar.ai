# IAQAR.AI — Event Workflow

Version 1.0 · Documents the approved event‑driven workflow across ingestion,
analysis, matching, operations, notifications and cooperation. Implemented with a
database‑backed job/outbox pattern on the existing stack (no new broker).

## 1. Canonical flow

```
SOURCE_RECEIVED
 → SOURCE_STORED
 → ANALYSIS_REQUESTED
 → DATA_EXTRACTED
 → OPPORTUNITY_CREATED_OR_UPDATED
 → DATA_COMPLETENESS_EVALUATED
 → MATCHING_REQUESTED
 → MATCH_CREATED
 → OPERATION_CREATED
 → NOTIFICATION_CREATED
 → BROKER_ACTION
 → MESSAGE_DRAFT_CREATED
 → EXTERNAL_RESPONSE_RECEIVED
 → NEXT_OPERATION_CREATED
 → COMPLETED
```

## 2. Handler contract

Every event handler must be:

- **Idempotent** — reprocessing the same event/id produces no duplicate
  Opportunity, Match, Operation, notification, or cooperation request.
- **Retry‑safe** — safe to re‑run after partial failure.
- **Tenant‑aware** — always scoped by `officeId`.
- **Auditable** — records what happened for critical actions.
- **Failure‑isolating** — a failed external integration records a failure state
  and never corrupts the Opportunity.

## 3. Deduplication signals (Directive §24)

Same source message id · same normalized URL · same uploaded‑file checksum · same
external webhook event id · same office + normalized content fingerprint · same
Opportunity pair in matching. When uncertain, link a possible duplicate for
review rather than silently merging broker‑confirmed data.

## 4. Matching (Directive §14–15)

Matching runs **automatically** on relevant events (new offer/request, owner or
customer submission, data completion, relevant update, new external source,
cooperation‑scope change). It is idempotent per
`(canonical opportunity pair, matching rule version, relevant data version)` and
uses **configurable thresholds** (not hard‑coded in the UI). Only actionable
results create an Operation, and a notification is sent only when appropriate.

## 5. Operations Center (Directive §16)

Operations are actionable work items generated by internal engines — never the
matching engine itself, never every saved Opportunity, never queue/log noise. An
Operation carries `deduplicationKey`; the same action + source event must not
create multiple open Operations. States: `OPEN`, `IN_PROGRESS`,
`WAITING_EXTERNAL_RESPONSE`, `COMPLETED`, `DISMISSED`, `EXPIRED`.

## 6. Notifications (Directive §17)

Routed to the correct office/broker, respecting `notificationPrefs`, linked to
the related Operation, deduplicated, auditable, and preview‑safe on locked
devices. Preserve existing FCM/PWA behaviour; provide an in‑app fallback when
push permission is unavailable.

## 7. Cooperation events (Directive §19–20)

Modes: `DISABLED`, `APPROVAL_REQUIRED` (default), `SMART_AUTOMATIC`. Sharing is
opt‑in, scoped, revocable, read‑only by default, minimum data, contact hidden by
default. Ownership metadata (originating office/broker, original `createdAt`) is
always preserved. Automatic cooperation never auto‑exposes private contact info.

## 8. Phase status

Phase 1 (current) introduces the **cooperation mode** and **notification
preference** settings that later phases' handlers will read. The event handlers
themselves (analysis, matching, operations, notifications, cooperation) are
delivered in Phases 2–7.
